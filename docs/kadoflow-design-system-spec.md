# Kadoflow: дизайн-концепция, интерактивные фичи и fluid responsive

> Рабочая спецификация для Codex и других AI-агентов, участвующих в проектировании и разработке сайта Kadoflow.

## 1. Контекст проекта

Kadoflow — авторская студия по созданию выразительных сайтов и цифровых продуктов.

Слоган:

> **Kadoflow — свобода формы, порядок процесса.**

Визуальный язык должен сочетать:

- минимализм и чёткую композиционную сетку;
- ощущение аккуратности, воздуха и порядка;
- небольшое количество необычных интерактивных деталей;
- современную digital-эстетику;
- сдержанные восточные и японские ассоциации без буквальных клише;
- выразительную типографику;
- плавное, физически правдоподобное движение.

Стек проекта:

- Vue;
- Nuxt (по умолчанию **SSG** — статическая генерация);
- Tailwind CSS;
- SVG, Canvas 2D и при необходимости WebGL;
- Figma для макетов и дизайн-токенов.

Принцип поставки: публичный сайт отдаётся статикой (CDN / static hosting), без обязательного VPS. SSR/сервер — только если задача клиента этого требует. Подробнее — в `docs/brand-and-website-brief.md` → «Техническая поставка: SSG-first».

Главный принцип визуала: эффекты должны объяснять характер бренда, а не быть случайным набором анимаций.

## 2. Система fluid responsive

### 2.1. Базовые контрольные ширины

Использовать четыре основных макета — ровно столько, сколько нужно для смены композиции, без лишних режимов «на всякий случай»:

| Режим | Ширина макета | Назначение |
| --- | ---: | --- |
| Mobile | `390px` | Главный мобильный канон (iPhone / Safari) |
| Tablet | `768px` | Планшет и смена раскладки |
| Desktop | `1280px` | Основной десктопный макет |
| Wide | `1440px` | Верх fluid-шкалы и потолок токенов type/space |

Почему такой набор:

- `390` — проектируем mobile вокруг iPhone/Safari; Android обычно спокойно наследует. Stress-test отдельно: `360`, `375`, `430`, landscape.
- `768` — типичная смена структуры (колонки, навигация, иерархия блоков).
- `1280` — рабочий desktop, на котором собирается основная композиция.
- `1440` — потолок осмысленного роста типографики и ритма. Раньше здесь стояло `1920`; для type/space это слишком широко и провоцирует «тупой зум» к 4K.
- Пятую точку (`1024` и т.п.) добавлять только если на ней реально другой layout (например, desktop-nav раньше `1280`). Иначе лишний Figma-mode и лишний стык `clamp`.

Контрольные ширины — не четыре жёстких сайта. Они задают:

1. точные значения токенов в ключевых точках (Figma = браузер);
2. моменты структурного изменения композиции (breakpoints);
3. границы кусочной fluid-интерполяции.

Сохранение композиции **не равно** пропорциональному зуму всего UI под ширину монитора. Растёт только то, чему это полезно; остальное упирается в потолок и `max-width` контентной оболочки. Фон и Flow Surface могут оставаться full-bleed.

### 2.2. Разделение ответственности

Использовать два разных механизма:

#### Breakpoints

Меняют структуру интерфейса:

- количество колонок;
- направление `flex`;
- расположение текста и изображений;
- вид навигации;
- порядок блоков;
- появление или скрытие отдельных элементов.

#### Fluid values

Плавно меняют размеры внутри диапазона:

- размер шрифта;
- межстрочный интервал;
- отступы;
- `gap`;
- размеры декоративных элементов;
- радиусы;
- ширину отдельных компонентов;
- вертикальный ритм.

Не следует равномерно масштабировать весь сайт одним коэффициентом. Типографика, интервалы, медиа и контейнеры должны расти с разной скоростью и иметь разные потолки.

#### Что зумится, что нет

| Слой | Поведение после Wide (`1440`) |
| --- | --- |
| `type/*`, основной vertical rhythm | Замирают на wide-значениях |
| `layout/gutter`, мелкие gaps | Могут чуть дышать или тоже замирать — решать по макету |
| Контентная колонка | `max-width` (ориентир `1200–1440`), дальше воздух по бокам |
| Фон, Flow Surface, декоративные плоскости | Могут занимать весь viewport |
| Сетка карточек / медиа внутри колонки | Через `fr` / `minmax` / container, не через global zoom |
| 1px линии, touch-targets, мелкие иконки | Дискретные, не fluid |

Цель: сайт на ультрашироком и 4K ощущается как та же композиция в комфортной мере (как Cursor), а не как увеличенный скрин 1280.

### 2.3. Связь Figma и CSS

На контрольных ширинах значение в Figma должно совпадать со значением в браузере:

- `24px` в макете `390px` → `24px` в CSS при viewport `390px`;
- `32px` в макете `768px` → `32px` в CSS при viewport `768px`;
- и так далее.

Между контрольными точками браузер вычисляет промежуточные значения. Они могут быть дробными:

```text
24px → 24.73px → 27.18px → 32px
```

Это нормально. Браузер поддерживает субпиксельный рендеринг. Не округлять fluid-значения вручную.

Исключения, которые обычно остаются дискретными:

- линии толщиной `1px`;
- размеры небольших интерфейсных иконок;
- минимальные touch-targets;
- значения, влияющие на pixel-perfect совмещение;
- отдельные размеры логотипа.

### 2.4. Figma Variables

Создать коллекцию `Responsive` с режимами:

- `Mobile / 390`;
- `Tablet / 768`;
- `Desktop / 1280`;
- `Wide / 1440`.

Начальный набор токенов:

| Token | 390 | 768 | 1280 | 1440 |
| --- | ---: | ---: | ---: | ---: |
| `layout/gutter` | 20 | 32 | 48 | 64 |
| `layout/grid-gap` | 16 | 24 | 32 | 36 |
| `layout/content-max` | — | — | 1200 | 1320 |
| `space/section` | 80 | 112 | 160 | 200 |
| `space/block` | 32 | 48 | 64 | 80 |
| `type/body` | 16 | 17 | 18 | 19 |
| `type/display` | 48 | 72 | 96 | 112 |
| `radius/card` | 16 | 20 | 24 | 28 |

Это стартовые значения, а не финальная неизменяемая шкала. Их необходимо проверить на реальном контенте. Display на `1440` намеренно ниже старого «1920 → 128»: потолок букв важнее заполнения экрана.

В Figma:

- использовать Auto Layout;
- предпочитать `Fill container` и `Hug contents`;
- задавать `min/max width`, где возможно;
- не фиксировать ширину каждого блока вручную;
- собирать интерфейс на сетке и компонентах;
- переключать Variable Mode для проверки четырёх контрольных состояний.

Figma показывает контрольные состояния. Истинное поведение между ними проверяется в браузере.

### 2.5. Формула fluid-интерполяции

Для двух точек:

```text
viewport: v1 → v2
size:     s1 → s2
```

Использовать:

```text
slope = (s2 - s1) / (v2 - v1)
intercept = s1 - slope × v1
```

Результат:

```css
clamp(
  min-size,
  calc(intercept + slope * 100vw),
  max-size
)
```

Интерполяция должна быть кусочной:

- `390 → 768`;
- `768 → 1280`;
- `1280 → 1440`.

Пример для горизонтального gutter:

```css
:root {
  --layout-gutter:
    clamp(20px, calc(7.62px + 3.175vw), 32px);
}

@media (min-width: 768px) {
  :root {
    --layout-gutter:
      clamp(32px, calc(8px + 3.125vw), 48px);
  }
}

@media (min-width: 1280px) {
  :root {
    --layout-gutter:
      clamp(48px, calc(-80px + 10vw), 64px);
  }
}
```

Соседние формулы обязаны давать одинаковое значение в общей контрольной точке, иначе на breakpoint появится скачок.

После `1440` fluid-формула больше не поднимает потолок: действует wide-значение токена.

### 2.6. Поведение на 4K и ultra-wide

Не масштабировать интерфейс бесконечно вместе с viewport.

После `1440px` по умолчанию:

- типографика и основной ритм фиксируются на wide-значениях;
- внутренний контент ограничивается `layout/content-max` (и/или секционным `max-width`);
- фоновые поверхности и декоративные элементы могут продолжать занимать ширину экрана;
- ширины карточек и медиа определяются сеткой, `fr`, `minmax()` и размером контейнера, а не фиксированными пикселями и не global zoom.

Так размер элемента сохраняет отношение к рабочей композиции, а не к физической ширине 4K-монитора.

Container queries — точечно для компонентов внутри колонки, не как замена page-level fluid и не как способ «продолжить зум» на 4K.

Отдельный диапазон `1440 → 2560` для type/space по умолчанию **не** вводить. Если редкий проект правда должен быть immersive fullscreen на 4K — это исключение проекта, не правило системы Kadoflow.

### 2.7. Архитектура токенов и Tailwind

Желательно хранить исходные значения независимо от Figma и CSS:

```json
{
  "viewports": [390, 768, 1280, 1440],
  "tokens": {
    "layout.gutter": [20, 32, 48, 64],
    "space.section": [80, 112, 160, 200],
    "type.display": [48, 72, 96, 112]
  }
}
```

Из источника генерировать:

- Figma Variables;
- CSS Custom Properties с кусочными `clamp()`;
- Tailwind theme (маппинг утилит на эти переменные);
- документацию.

**Решение по Tailwind:** да, используем Tailwind CSS как основной utility/layer для вёрстки Kadoflow и клиентских проектов на той же системе.

Почему подходит:

- быстрая итерация рядом с Figma (токен → utility → проверка на контрольных ширинах);
- удобно держать breakpoints и semantic-классы (`text-display`, `p-section`, `max-w-content`) в одном месте;
- хорошо стыкуется с Nuxt/Vue;
- не мешает кусочному fluid, если foundation — CSS-переменные, а не ad-hoc `~`-классы.

Как не использовать Tailwind:

- не строить fluid на [fluid.tw](https://fluid.tw/) как на фундаменте (один отрезок min→max плохо бьётся с кусочной шкалой);
- не размазывать «магические» arbitrary values вместо токенов;
- не подменять структурные breakpoints одним global scale.

Вспомогательные инструменты:

- [Utopia](https://utopia.fyi/) — калькулятор/референс шкалы;
- [Tokens Studio](https://docs.tokens.studio/) — Figma variables;
- [Style Dictionary](https://styledictionary.com/) — генерация платформенных значений при росте системы.

Не превращать в токены каждую случайную ширину блока. Токенизировать:

- типографику;
- повторяемые интервалы;
- gutter и grid gap;
- радиусы;
- размеры элементов управления;
- контейнеры / content-max;
- повторяемые motion-параметры.

Остальную геометрию строить через Grid, Flexbox, `fr`, `minmax()`, `aspect-ratio` и точечные container queries.

## 3. Визуальная глубина первого экрана

На фоне первого экрана расположен прямоугольник, немного темнее основного фона сайта.

Назначение:

- создать дополнительный пространственный слой;
- визуально собрать контент;
- поддержать идею порядка и структуры;
- стать поверхностью для интерактивного паттерна.

Слои:

1. основной фон страницы;
2. статичная более тёмная поверхность;
3. интерактивный паттерн;
4. типографика и контент;
5. кейс/изображение, частично выходящее за границу поверхности.

Изображение или видео намеренно выступает за нижнюю границу прямоугольника, создавая ощущение глубины.

Реализация:

- поверхность можно сделать псевдоэлементом секции;
- секция должна иметь `position: relative` и `isolation: isolate`;
- нельзя обрезать выступающее медиа через `overflow: hidden`;
- контент и медиа должны находиться над поверхностью по `z-index`;
- разница оттенков должна быть заметной, но спокойной.

## 4. Физика слов «свобода» и «формы.»

Слова:

- `свобода`;
- `формы.`

должны физически реагировать на приближение курсора.

Фраза `порядок процесса.` остаётся неподвижной. Это создаёт смысловой контраст:

- свобода формы физически подвижна;
- порядок процесса стабилен и привязан к сетке.

### 4.1. Поведение

Каждое подвижное слово:

- получает мягкий импульс от курсора;
- имеет скорость и инерцию;
- возвращается к исходной позиции пружиной;
- имеет затухание;
- не может уйти дальше заданного радиуса;
- слегка покачивается после взаимодействия и затем успокаивается.

Начальные параметры:

```ts
const MAX_DISTANCE = 48
const CURSOR_RADIUS = 140
const REPULSION = 0.7
const SPRING = 0.035
const DAMPING = 0.88
```

Параметры необходимо вынести в motion-токены и уточнить визуально.

Базовая модель:

```text
acceleration = cursorRepulsion + springToOrigin
velocity = (velocity + acceleration) × damping
position += velocity
position = clampToRadius(position, maxDistance)
```

### 4.2. Структура элемента

Использовать неподвижный anchor и движущийся внутренний элемент:

```html
<span class="word-anchor">
  <span class="word-body">свобода</span>
</span>
```

Измерять координаты относительно `.word-anchor`, а трансформировать только `.word-body`.

Это предотвращает дрожание и ситуацию, когда hit-area начинает двигаться вместе со словом.

Рекомендуемый интерфейс Vue-компонента:

```vue
<PhysicsWord
  :max-distance="48"
  :cursor-radius="140"
>
  свобода
</PhysicsWord>
```

Не использовать Matter.js без необходимости. Для двух слов достаточно небольшой spring-модели на `requestAnimationFrame`.

## 5. Cursor influence field и интерактивный паттерн

Референс: [Immersive Garden](https://immersive-g.com/).

Вместо полноценного 3D использовать локальное 2D-поле воздействия.

Паттерн располагается внутри фоновой поверхности и в спокойном состоянии:

- практически незаметен;
- имеет очень низкий контраст;
- выглядит регулярным и упорядоченным.

В области курсора паттерн:

- становится заметнее;
- приобретает псевдорельеф;
- слегка деформируется;
- начинает медленно двигаться;
- затухает не мгновенно, а с небольшим шлейфом.

Не делать очевидный светящийся круг. Граница зоны должна быть очень мягкой.

### 5.1. Визуальное направление

Предпочтительный паттерн — модульная прямоугольная сетка:

- в покое строгая и геометричная;
- под воздействием курсора ячейки смещаются, размыкаются или изгибаются;
- может отдалённо напоминать структуру японских сёдзи;
- не должна выглядеть как буквальный этнический орнамент;
- квадратная геометрия связывается с пиксельными эффектами изображений.

Альтернативные варианты:

- тонкие контурные линии потока;
- разорванная архитектурная сетка;
- квадратные пиксельные модули;
- псевдобумажный рельеф из двух смещённых светлого и тёмного слоёв.

Избегать шаблонных частиц, яркого glow и слишком очевидных топографических линий.

### 5.2. Общая физическая система

Cursor influence field должен быть общим источником воздействия:

- проявляет и деформирует паттерн;
- слегка двигает слова `свобода` и `формы.`;
- при необходимости влияет на отдельные декоративные элементы.

Не создавать для каждого эффекта отдельную несвязанную физику.

### 5.3. Desktop

Рекомендуемые параметры:

- радиус проявления: `180–240px`;
- мягкая граница;
- лёгкое запаздывание центра за курсором через `lerp`;
- усиление деформации при быстром движении;
- затухание следа: `400–700ms`.

Для MVP допустим SVG/CSS-паттерн с `mask-image: radial-gradient(...)`.

Для финальной версии предпочтителен единый Canvas 2D под контентом:

- `pointer-events: none`;
- одна система координат;
- локальная деформация паттерна;
- несколько затухающих точек воздействия;
- отсутствие постоянной перерисовки в покое.

WebGL использовать только если Canvas 2D не обеспечивает нужную деформацию или производительность.

### 5.4. Mobile

На мобильных устройствах нет постоянного курсора. Вместо фонарика использовать всполохи от касаний и свайпов:

- каждый touch-point создаёт локальную область проявления;
- область немного расширяется;
- паттерн получает короткий импульс;
- след исчезает за `600–900ms`;
- естественный вертикальный скролл страницы не должен блокироваться;
- эффект не должен требовать специального жеста.

Размер mobile-зоны следует подбирать с учётом того, что палец закрывает часть изображения.

## 6. Hover-эффект распада изображения на квадраты

На кликабельных изображениях кейсов нужен необычный hover-эффект, похожий на Zajno:

- изображение локально распадается или смещается квадратными фрагментами;
- область воздействия следует за курсором;
- искажение усиливается рядом с курсором;
- после ухода изображение собирается обратно;
- эффект не должен ухудшать читаемость превью.

Референсы:

- [Codrops: Interactive WebGL Hover Effects](https://tympanus.net/codrops/2020/04/14/interactive-webgl-hover-effects/);
- [демо](https://tympanus.net/Tutorials/webgl-mouseover-effects/step3.html);
- [MIT-репозиторий](https://github.com/akella/webgl-mouseover-effects).

Техническое направление:

- Three.js/WebGL + GLSL для финального варианта;
- один общий WebGL canvas или аккуратное переиспользование renderer;
- не создавать отдельный тяжёлый WebGL-контекст для каждой карточки;
- запускать рендеринг только при видимости и взаимодействии;
- на touch-устройствах использовать упрощённую реакцию на тап или статичный fallback.

Применять эффект только к ключевым кейсам, а не ко всем изображениям сайта.

## 7. Прогрессивная пиксельная загрузка изображений

Изображение должно появляться не через обычный blur, а через последовательное повышение детализации:

```text
крупные пиксели → средняя детализация → полное изображение
```

Пример этапов:

1. placeholder шириной около `24px`;
2. промежуточное изображение около `240px`;
3. полноразмерное оптимизированное изображение.

Во время первых этапов допустимо:

```css
image-rendering: pixelated;
```

После загрузки финального изображения `image-rendering` вернуть к обычному значению.

Базовая реализация может использовать возможности [Nuxt Image](https://image.nuxt.com/usage/nuxt-img) и собственный компонент для нескольких стадий.

Компонент должен:

- предотвращать layout shift через заданные размеры или `aspect-ratio`;
- использовать современные форматы;
- учитывать DPR;
- не загружать промежуточную стадию, если полное изображение уже находится в кеше;
- корректно работать без JavaScript как обычное изображение.

## 8. Иконки

Сайт небольшой, поэтому не подключать огромную библиотеку целиком.

Базовое направление:

- использовать [Iconoir](https://iconoir.com/) как основу;
- хранить необходимые SVG локально;
- применять `currentColor`;
- сохранить файл лицензии;
- выбрать около `8–12` действительно используемых иконок.

Базовые параметры:

- сетка `24 × 24`;
- stroke около `1.5`;
- округлённые `linecap` и `linejoin`;
- основной стиль outline;
- рабочие размеры `20px` и `24px`.

Ориентировочный набор:

- menu;
- close;
- arrow-right;
- arrow-up-right;
- chevron-down;
- play;
- pause;
- copy;
- mail;
- external-link;
- plus;
- minus.

Чтобы сделать набор более уникальным, модифицировать выбранные иконки в общей геометрии Kadoflow:

- разрыв части контура;
- сдвинутый угол;
- разделение формы на два модуля;
- собственная форма стрелки;
- повторяющийся мотив потока.

Официальные логотипы социальных сетей не перерисовывать в авторской геометрии.

## 9. Пространственная навигация Page Canvas

### 9.1. Концепция

Основная навигация открывается через кнопку-бургер как отдельный пространственный режим — условный **Page Canvas / Workspace**.

При открытии меню:

1. камера плавно отдаляется от текущей страницы;
2. страница превращается в один из фреймов общего пространства Kadoflow;
3. вокруг появляются фреймы остальных страниц;
4. пользователь выбирает новый фрейм;
5. камера направляется к нему, и выбранный фрейм разворачивается в полноценную страницу.

Механика должна напоминать рабочее пространство дизайнера с разложенными макетами, но не копировать интерфейс Figma буквально. Это часть идентичности Kadoflow и демонстрация пространственного веб-дизайна, а не стилизация под чужой продукт.

Навигация обязана оставаться понятной без знания этой метафоры: все страницы имеют крупные читаемые названия и являются обычными ссылками.

### 9.2. Композиция фреймов

На desktop фреймы раскладываются преимущественно по два в ряд. Их пропорции основаны на вертикальном листе, близком к A4, но размеры и положение немного различаются.

Разница между соседними фреймами должна быть контролируемой:

- размер отличается приблизительно на `5–15%`;
- допускается небольшой сдвиг относительно общей строки;
- сохраняется единая сетка и ясная визуальная иерархия;
- композиция не должна выглядеть как случайно разбросанные карточки.

Внутри фреймов используются специально подготовленные миниатюры страниц, а не буквальные скриншоты, уменьшенные до нечитаемого состояния. Миниатюра передаёт характер страницы через цвет, композицию и несколько крупных элементов.

Над или рядом с каждым фреймом размещаются:

- номер;
- название страницы;
- короткое функциональное описание;
- при необходимости техническая деталь вроде размера или координат.

Текущая страница остаётся видимой и получает нейтральную отметку `Вы здесь` или `Current frame`.

Базовая раскладка:

```text
[ Главная ]   [ Проекты  ]
[ Услуги  ]   [ О Kado   ]
[ Контакты ]  [ Служебный фрейм ]
```

Служебный фрейм может содержать язык, почту, социальные ссылки и актуальный статус приёма проектов. Он не должен притворяться отдельной страницей.

На дальнем плане допустимы едва заметные элементы рабочего пространства:

- направляющие;
- координаты;
- пустые рамки;
- точки привязки;
- частично обрезанные листы.

Они служат только для ощущения продолжающегося пространства и не должны выглядеть кликабельными.

### 9.3. Реакция камеры на курсор

Свободное перемещение полотна, drag средней кнопкой мыши и необходимость вручную возвращать камеру не используются. Для короткого навигационного сценария это создаёт лишнее правило и риск потерять меню.

Вместо этого применяется пассивный параллакс:

- положение курсора задаёт целевое смещение камеры;
- камера следует за целевой точкой через сглаживание или пружину;
- рабочее полотно и дальний фон движутся с разной скоростью;
- все основные фреймы всегда остаются доступными;
- при выходе курсора из viewport камера плавно возвращается в центр;
- при закрытии меню и переходе на другую страницу камера также сбрасывается.

Предпочтительное пространственное поведение: камера как будто поворачивается в сторону курсора, поэтому содержимое полотна немного смещается навстречу. На прототипе необходимо сравнить его с вариантом, в котором контент буквально следует за курсором.

Ориентировочные пределы:

- смещение камеры: `8–16px`;
- дополнительное смещение ближних фреймов: `2–5px`;
- смещение дальнего фона: `3–8px`;
- наклон фрейма: не более `0.3–0.6deg`, только если он действительно улучшает ощущение глубины.

При неподвижном курсоре камера сохраняет достигнутую позицию. Автоматический возврат через каждую секунду не используется, чтобы пространство не двигалось само по себе.

### 9.4. Связь с остальным сайтом

Flow Surface остаётся элементом самой страницы и не превращается в декоративный слой меню. При отдалении текущей страницы поверхность естественно остаётся видна внутри её фрейма.

В результате пользователь обнаруживает, что уже знакомая живая поверхность является частью одного из макетов в общем пространстве Kadoflow. Это создаёт эффект четвёртой стены без второй конкурирующей глобальной механики.

Навигационное пространство использует общую палитру, типографику, физику движения и motion-токены сайта.

### 9.5. Mobile

На touch-устройствах режим свободного пространства и параллакс камеры отключаются.

Страницы представлены горизонтально расположенными фреймами:

- обычный свободный touch-scroll;
- мягкий `scroll-snap`;
- часть следующего фрейма видна у края экрана;
- активная страница выделена;
- подписи остаются крупными и читаемыми;
- никакой hover-информации, необходимой для выбора страницы.

Это тот же образ рабочего стола, адаптированный к естественному мобильному жесту, а не уменьшенная desktop-сцена.

### 9.6. Курсор и состояния взаимодействия

Не заменять системный курсор на постоянно рисуемую пользовательскую стрелку.

Вместо этого:

- сохранять системный курсор в основном интерфейсе;
- в Page Canvas при наведении на фрейм добавлять компактную подпись `Открыть`, `View` или название страницы;
- использовать отдельные состояния курсора над Flow Surface и другими действительно интерактивными зонами;
- полностью отключать декоративный курсор при `pointer: coarse`;
- не использовать пользовательский курсор как единственный способ сообщить действие.

### 9.7. Скорость, доступность и fallback

Открытие Page Canvas должно занимать ориентировочно `500–800ms`: достаточно, чтобы почувствовать отдаление камеры, но без ощущения заставки при каждом переходе.

Обязательные требования:

- закрытие по `Esc`;
- удержание keyboard focus внутри открытого меню;
- видимый `focus` для каждого фрейма;
- восстановление focus на кнопке меню после закрытия;
- обычные ссылки и рабочая навигация без анимаций;
- запрет взаимодействия с контентом страницы под открытым меню;
- сохранение или предсказуемое восстановление позиции прокрутки;
- упрощённая статичная композиция при `prefers-reduced-motion: reduce`;
- отсутствие параллакса для touch и coarse pointer;
- отсутствие тяжёлых live-снимков DOM для миниатюр.

При reduced motion текущая страница может быстро уменьшаться через короткий `opacity/scale` transition либо меню может открываться как статичная сетка без имитации движения камеры.

- анимация не должна мешать чтению и кликам.

## 11. Производительность и доступность

Обязательные требования:

- учитывать `prefers-reduced-motion: reduce`;
- отключать или сильно упрощать hover-эффекты при `pointer: coarse`;
- использовать `transform` и `opacity` для DOM-анимаций;
- ограничить Canvas DPR, например `Math.min(devicePixelRatio, 1.5–2)`;
- не выполнять `requestAnimationFrame`, если сцена не движется;
- останавливать эффекты вне viewport;
- очищать listeners, RAF, textures и WebGL resources при unmount;
- использовать `IntersectionObserver` для тяжёлых секций;
- обеспечить рабочий статичный fallback;
- не блокировать scrolling на touch-устройствах;
- тестировать на реальном iPhone/Safari, а не только через DevTools.

Особое внимание iOS/Safari:

- safe-area через `env(safe-area-inset-*)`;
- различия `svh`, `dvh` и `lvh`;
- изменение высоты viewport при появлении browser chrome;
- производительность Canvas/WebGL;
- поведение touch и pointer events;
- отсутствие hover как обязательного способа получить информацию.

### 11.1. Правила iOS-first (обязательные)

Kadoflow проектируется и принимается с приоритетом **iPhone + iOS Safari**. Если сценарий красиво работает в Chrome DevTools, но ломается на реальном iPhone — он не готов.

#### Viewport и высота

- Для полноэкранных секций предпочитать `dvh` / `svh`, не полагаться на голый `100vh`.
- Не рассчитывать layout на постоянную высоту browser chrome: адресная строка появляется и скрывается.
- Учитывать `safe-area-inset-*` для fixed-шапки, CTA, нижней навигации и notch/Dynamic Island.
- Проверять portrait и landscape; landscape на iPhone не должен ломать hero и меню.

#### Скролл и жесты

- Не блокировать нативный скролл (`overflow: hidden` на `body` только на короткое время открытых оверлеев и с восстановлением позиции).
- Не подменять вертикальный скролл кастомным wheel/touch hijack.
- `position: sticky/fixed` проверять на реальном устройстве: iOS часто даёт 1px-щели и прыжки при rubber-band.
- Rubber-band overscroll не должен открывать «дыру» под фон или ломать Flow Surface.

#### Рендеринг и perf

- Анимировать в основном `transform` и `opacity`; избегать анимации `filter`, больших `box-shadow` и постоянных blur на скролле.
- Canvas/WebGL: один контекст максимум, пауза вне viewport, DPR cap.
- Видео: `playsinline`, poster, без autoplay со звуком; останавливать вне viewport.
- Не держать бесконечный RAF «на всякий случай».
- Тяжёлые эффекты отключать или упрощать при low-power / слабом FPS, не ждать жалобы пользователя.

#### Touch и hover

- Вся информация и все действия доступны без hover.
- Touch-target не меньше ~44×44px.
- Hover-only курсорные эффекты на iOS не существуют как UX — давать tap/focus аналоги или смириться с упрощением.
- `100ms` click delay больше не главная боль, но `touch-action` и жесты свайпа меню нужно проверять руками.

#### Типографика и формы

- Не ставить `input`/`textarea` font-size ниже `16px` на mobile — иначе iOS зумит страницу при фокусе.
- После закрытия клавиатуры проверять, что scroll/viewport восстановились.
- `meta viewport` без запрета user zoom как единственной «защиты layout».

#### Тест-матрица перед merge визуальных фич

Минимум:

- iPhone SE / узкий logical width;
- актуальный iPhone (notch / Dynamic Island);
- iOS Safari + иногда in-app browser (Telegram/Instagram);
- airplane / throttling для проверки без «тёплого» кэша.

## 12. Порядок реализации

### Принцип работы

Верстаем **секция за секцией**. Каждую секцию доводим до полной адаптивности на контрольных ширинах `390 / 768 / 1280 / 1440` (и промежутках), прежде чем переходить к следующей.

Так fluid-система проверяется в бою сразу, а не «сначала весь desktop, потом адаптив сверху».

Внутренние страницы и сложная навигация (Page Canvas / workspace-меню) — после того, как главная собрана по секциям.

Заглушки ссылок в шапке допустимы до реализации маршрутов.

### Этап 1. Fluid foundation (обязателен до первой секции)

До hero и Flow Surface:

1. поднять Nuxt SSG + Tailwind;
2. зафиксировать контрольные ширины `390 / 768 / 1280 / 1440`;
3. описать responsive-токены (type, space, gutter, radius, content-max);
4. сгенерировать кусочные `clamp()` между брейкпоинтами;
5. собрать базовую сетку, оболочку `max-width` и типографику;
6. проверить отсутствие скачков на стыках breakpoint и промежуточные ширины;
7. smoke-check на реальном iPhone (хотя бы foundation).

Без этого нельзя честно верстать «секцию полностью адаптивно».

### Этап 2. Главная — секция за секцией

Для каждой секции один и тот же цикл:

1. desktop-композиция по макету;
2. fluid-токены и структурные breakpoints;
3. motion / интерактив секции (с reduced-motion и touch fallback);
4. проверка `360–1440+`, iOS Safari;
5. только потом — следующая секция.

Ориентировочный порядок секций главной (уточняется по финальному макету):

1. оболочка страницы + шапка (ссылки-заглушки ок);
2. hero + первая форма Flow Surface;
3. блок «о Kadoflow» / подход;
4. кейсы (по одному или общей лентой — как в макете);
5. контактный сценарий на главной;
6. подвал.

Page Canvas-навигацию в этом этапе не блокируем как зависимость: достаточно обычной шапки.

### Этап 3. Пространственная навигация

- собрать статичную композицию Page Canvas;
- подготовить специальные миниатюры страниц;
- реализовать отдаление и приближение камеры;
- добавить низкоамплитудный desktop-параллакс;
- собрать горизонтальную mobile-ленту со `scroll-snap`;
- реализовать keyboard и reduced-motion состояния;
- проверить переходы между страницами и восстановление scroll/focus.

### Этап 4. Единое поле

- перенести паттерн на Canvas 2D;
- связать поле с физикой слов;
- реализовать затухающий desktop trail;
- реализовать touch-всполохи;
- оптимизировать цикл рендеринга.

### Этап 5. Кейсы и изображения

- сделать progressive pixel loading;
- добавить WebGL-hover на ключевые карточки;
- реализовать fallback для touch/reduced-motion;
- проверить производительность на слабых устройствах.

### Этап 6. Полировка

- собрать локальный набор иконок;
- унифицировать easing, duration и spring tokens;
- проверить клавиатурную навигацию;
- проверить контраст;
- провести тесты на iOS Safari, Android Chrome, macOS Safari и Windows Chrome.

## 13. Инструкции для Codex

При работе над Kadoflow:

1. Сохранять концептуальный контраст «свобода формы / порядок процесса».
2. Не добавлять визуальный эффект без смысловой функции.
3. Сначала реализовывать лёгкий прототип, затем усложнять после визуальной проверки.
4. Использовать один общий источник pointer/touch-взаимодействия для связанных эффектов.
5. Не привязывать всю композицию к фиксированным пикселям.
6. Не заменять breakpoint-логику одним глобальным масштабированием.
7. Сохранять точные значения на контрольных ширинах и fluid-переходы между ними.
8. Использовать CSS Grid/Flexbox для структуры и `clamp()` для подходящих размерных токенов.
9. Любой интерактив должен иметь mobile, reduced-motion и static fallback.
10. При выборе между эффектностью и стабильностью отдавать приоритет стабильной композиции и производительности.

Перед реализацией каждой крупной фичи Codex должен:

- сформулировать визуальное поведение;
- определить desktop/mobile/reduced-motion состояния;
- выбрать минимально достаточную технологию;
- указать параметры, которые следует вынести в токены;
- после реализации проверить промежуточные viewport-ширины, а не только четыре макета.
